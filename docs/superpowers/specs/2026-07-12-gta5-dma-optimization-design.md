# GTA5 DMA 渐进式优化重构设计

## 背景

当前主工程为 `GTA5_DMA/GTA5_DMA.sln`，使用 Visual Studio C++、DirectX 11、ImGui 和 MemProcFS，支持 GTA5 原版与 Enhanced。`Release|x64` 已建立成功编译基线。当前没有明确的运行故障，优化目标是提高稳定性和运行效率，并降低后续维护成本，同时保持现有功能、界面、快捷键和配置行为不变。

工程包含大量历史副本，但本次只修改根目录下的 `GTA5_DMA` 主工程。历史目录、第三方 ImGui 源码、MemProcFS 头文件和游戏偏移不属于本次重构范围。

## 目标

1. 让程序初始化、运行和退出过程具有明确且可验证的生命周期。
2. 加强 DMA 地址解析、内存读写和跨线程状态的失败保护。
3. 减少循环中的重复 DMA 读取与无意义写入，不牺牲地址更新正确性。
4. 拆分职责过多的大型源文件，使功能模块更容易理解和修改。
5. 在每一批修改后维持可编译、可运行、可回归的状态。

## 非目标

- 不增加新的游戏功能。
- 不改变游戏数值、现有功能语义、菜单布局或快捷键。
- 不更新 GTA5 偏移，不改变原版与 Enhanced 的识别规则。
- 不重写 ImGui、MemProcFS 或 DirectX 后端。
- 不一次性替换现有架构，不清理历史副本目录。

## 总体策略

采用渐进式重构。每个阶段独立编译并在真实 DMA 硬件与 GTA5 环境中回归，只有上一阶段稳定后才进入下一阶段。公开类名和现有功能入口保持兼容；结构拆分通过内部委托逐步完成，避免稳定性修复、性能调整和大型文件拆分混在同一个变更中。


## 新 UI 设计

### 兼容原则

- UI 重构只改变呈现层，不改变 DMA 初始化、地址解析、读取、写入和功能类调用路径。
- 保留全部现有功能入口、默认值、开关语义、游戏数值、快捷键和原版/Enhanced 版本识别逻辑。
- UI 状态继续绑定现有功能模块公开状态，不把 DMA 访问逻辑移动到渲染代码中。
- 新界面迁移期间保留旧菜单实现作为可回退路径；只有全部模块完成编译和实机回归后才移除旧菜单调用。

### 布局

新界面采用紧凑双栏控制台布局，并继续使用 ImGui 与 DirectX 11：

- 默认窗口尺寸约为 `900x620`，允许用户自由缩放。
- 最小窗口尺寸约为 `760x520`，避免文字、按钮和参数控件重叠。
- 顶部栏显示产品名称、当前游戏版本和 DMA 连接状态。
- 左侧上方提供无敌、通缉、隐身和碰撞等常用功能的快速控制。
- 左侧下方使用稳定宽度的模块导航，包含人物、载具、武器、传送、任务和设置。
- 右侧为可扩展的当前模块参数区，窗口放大时优先扩展该区域。
- 底部状态栏显示目标进程、DMA 运行或读取状态以及 END 退出提示。
- 窗口变小时，长内容通过换行或独立滚动处理，不压缩到文字重叠。

### 视觉风格

采用中性蓝灰的专业桌面工具风格：

- 深灰黑作为窗口和工作区背景，中性灰用于边框、分隔线和次要文字。
- 蓝色只用于当前导航、启用状态和关键交互反馈。
- 成功、警告和错误分别使用克制的绿色、琥珀色和红色。
- 控件圆角保持在约 `3-5px`，不使用渐变、发光球或大面积装饰。
- 通过间距、分隔线和对齐建立信息层级，不使用装饰性嵌套卡片。
- 界面文字以中文为主，保留进程名、PID 和 DMA 等必要技术标识。

### ImGui 实现约束

- 主要布局使用 `BeginChild`、`BeginTable`、`Selectable` 和分隔线实现。
- 二进制功能使用复选框或紧凑开关；数值使用滑块、拖动数值或步进输入框。
- 模式和选项集合使用组合框或分段选择，长参数列表使用表格对齐标签和值。
- 模块内容区域独立滚动，左侧导航宽度保持稳定。
- 危险或立即执行的操作与普通状态开关分区，降低误触风险。
- 不在 ImGui 每帧渲染路径中创建不必要的线程、执行初始化或增加新的高频 DMA 访问。

## 阶段一：建立保护基线

- 保存 `Release|x64` 和 `Debug|x64` 的构建结果与项目自身警告清单。
- 建立人工回归清单，覆盖 DMA 初始化、游戏版本识别、主菜单、人物、载具、武器、传送、抢劫分红和正常退出。
- 记录关键场景：进入游戏、上下车、角色死亡重生、切换战局、游戏进程退出后重新连接，以及按 END 退出工具。
- 将第三方 MemProcFS 头文件产生的 C4200 警告与项目自身警告分开管理，不直接修改第三方声明。

## 阶段二：稳定性优化

### 线程与生命周期

- 将跨线程运行标志改为原子状态，并集中控制停止请求。
- 只允许一个 DMA 后台循环运行，消除 `main.cpp` 与 `ModeSelector.cpp` 可能形成的重复启动路径。
- 不保留无法等待的 detached DMA 线程；退出时先请求停止，再等待后台线程结束，随后关闭 DMA 和 ImGui 资源。
- 初始化失败必须可见且可退出，不能留下无效循环或半初始化资源。

### DMA 访问保护

- 为 DMA 句柄、PID、基础地址和解析出的对象地址建立统一有效性检查。
- 多级指针接口显式拒绝空 offset 列表，逐级检查读取字节数和空地址。
- 读取失败不覆盖上一份有效 UI 状态；写入失败必须向调用方返回失败。
- 修正返回成功但底层写入未验证的路径，并避免对零地址执行读写。
- 修复 `PlayerChaser.cpp` 中 `size_t` 到 `DWORD` 的潜在窄化警告。

### 共享状态

- 区分 UI 请求值、后台线程应用值和最近一次成功读取值。
- 跨线程布尔值和数值使用原子变量或受锁保护的数据结构，不依赖普通全局变量的偶然可见性。
- 保留现有开关行为，不在稳定性阶段更改刷新频率或游戏数值。

## 阶段三：性能优化

- 统计后台循环中各功能的 DMA 读取、地址解析和写入位置，先优化可证明重复的访问。
- 在单次更新周期内创建玩家状态快照，复用本地玩家、导航、玩家信息、载具、武器管理器等已成功解析的地址。
- 功能关闭时跳过对应读取；目标值与已应用值一致时跳过重复写入。
- 按数据变化速度划分刷新周期：生命周期与关键指针保持高频校验，低变化配置和非活动页面降低刷新频率。
- 上下车、角色重生、切换战局和游戏重载时立即使相关缓存失效，不长期缓存可能变化的对象地址。
- UI 渲染线程只读取稳定快照，不直接承担批量 DMA 更新工作。

性能优化以减少无效访问为目标，不通过降低关键功能响应速度换取指标。若真实回归发现延迟增加，则恢复对应功能原有刷新策略。

## 阶段四：结构重构

### 菜单模块

`MenuManager.cpp` 保留主菜单协调职责，将人物、载具、武器、传送和抢劫相关页面逐步拆到独立实现文件。新界面统一采用已确认的紧凑双栏布局和中性蓝灰主题。现有功能入口和公开调用方式保持不变；控件按新布局重新分组，但不改变其绑定状态和行为。

### 载具编辑模块

`VehicleEditor.cpp` 按以下职责拆分：

- 载具地址与状态读取。
- 属性修改和写入。
- 预设与批量操作。
- ImGui 界面渲染。

拆分期间保留 `VehicleEditor` 现有公共接口，由原类委托给内部组件，确保调用方无需同步大改。

### 通用基础能力

- 提取受检的 DMA 读取、写入和多级指针解析辅助接口。
- 集中管理运行状态和每周期快照，减少各模块自行维护重复全局变量。
- 仅在出现明确重复和稳定边界时增加抽象，不建立通用插件系统或额外框架。

## 验证策略

### 构建验证

- 使用 Visual Studio MSBuild 构建 `Debug|x64`。
- 使用 Visual Studio MSBuild 构建 `Release|x64`。
- 每批修改不得新增项目自身编译警告；第三方头文件警告单独记录。

### 实机回归

每个阶段至少执行一次完整回归：

1. DMA 硬件连接后启动工具，确认能识别 GTA5 原版或 Enhanced。
2. 打开并关闭各菜单页面，确认界面布局和交互未改变。
3. 分别验证人物、载具、武器、传送、时间、通缉、碰撞、隐身和抢劫分红入口。
4. 验证上下车、死亡重生和切换战局后的状态更新。
5. 关闭游戏进程并重新启动，确认工具不会崩溃或保留危险旧地址。
6. 使用 END 键退出，确认后台线程和窗口正常结束，无卡死和残留进程。

涉及游戏内存写入的具体效果由用户在受控环境中确认；自动化验证聚焦纯地址计算、状态转换和生命周期逻辑。

## 验收标准

- `Debug|x64` 与 `Release|x64` 均成功构建。
- 不新增项目自身编译警告，已知 `PlayerChaser.cpp` 窄化警告得到处理。
- 原有菜单、快捷键、功能入口、默认值和版本识别行为保持不变。
- 新界面默认约为 `900x620`，可缩放至不小于约 `760x520`，各尺寸下无文字或控件重叠。
- 顶部状态、左侧快速控制、模块导航、右侧参数区和底部状态栏均正常显示和交互。
- 初始化失败、游戏退出、重新连接和工具退出路径不会卡死或遗留后台线程。
- 开关关闭的功能不持续执行无意义 DMA 访问，重复写入明显减少。
- GTA5 原版和 Enhanced 的关键回归场景均通过实机测试。
- 大型文件拆分后公开接口保持兼容，单个变更可独立构建和回退。

## 变更管理

每一阶段拆成小批次提交。每批次只解决一种风险，并附带构建结果和适用的实机回归结果。若某项改动无法通过真实环境验证，则不与后续结构拆分合并，优先恢复到最近一次通过回归的状态。
